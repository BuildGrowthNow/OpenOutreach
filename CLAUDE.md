# CLAUDE.md

## Rules

- **Python env**: Always use `.venv/bin/python` (not system `python3`).
- **Commits**: No `Co-Authored-By` lines. Single-line messages (no body).
- **Deploy workflow**: After fixing issues, commit to main, wait ~4 min for GitHub Actions to deploy and restart Docker on the server, then verify on server.
- **Dependencies**: Managed in `requirements/*.txt` (used by local dev and Docker).
- **Docs sync**: When modifying code, update CLAUDE.md and ARCHITECTURE.md to reflect changes.
- **No memory**: Never use the auto-memory system (no MEMORY.md, no memory files). All persistent context belongs in CLAUDE.md or ARCHITECTURE.md.
- **Error handling**: App should crash on unexpected errors. `try/except` only for expected, recoverable errors. Custom exceptions in `exceptions.py`.
- **Logging**: Default console logging is INFO-level; set `OPENOUTREACH_LOG_LEVEL=DEBUG` only when debugging. Noisy third-party loggers such as `pymongo` stay at WARNING to avoid heartbeat spam.
- **No API backward compat**: Project has no external users yet — don't preserve old Python APIs, function signatures, or import paths. Rename, delete, and rewrite freely; no shims or re-export modules. MongoDB schema changes are additive by default — new fields can be added without migrations.
- **Post-task linting**: After completing a task, always run `make lint` and `make pyright` (or equivalent), then fix any issues before reporting the task as done.
- **Implementation docs**: When following a phased implementation document, don't create new docs — update the original with checkboxes (`- [x]`) to track completed steps.
- **Production-ready code**: All code (frontend, backend, daemon, desktop) must be production-ready. Search the codebase before writing new code — reuse and improve existing utilities, components, and patterns instead of duplicating. Refactor shared logic into common modules.
- **Frontend UI components**: Always use `shadcn@latest` components. Install new components with `npx shadcn@latest add <component> --yes`. Never implement custom UI components when shadcn has one available.

## Project Overview

OpenOutreach — self-hosted LinkedIn automation for B2B lead generation. Playwright + stealth for browser automation, LinkedIn Voyager API for profile data, FastAPI + MongoDB for backend (multi-tenant with JWT auth).

## Stack

FastAPI + MongoDB (zero Django). Multi-tenant with JWT auth. Multi-profile daemon manages one browser session per active LinkedInProfile, round-robins task execution across all users.

## Architecture (quick reference)

For detailed module docs, see `ARCHITECTURE.md`.

- **`linkedin_cli`** (external package — [`eracle/linkedin-cli`](https://github.com/eracle/linkedin-cli), installed from PyPI as `linkedin-agent-cli` via `requirements/base.txt`, unpinned so builds get the latest auto-published release; import name `linkedin_cli`): Framework-agnostic library of LinkedIn platform mechanics (browser nav/login, Voyager API, profile/conversation scrape, connect/message/status/thread verbs). Exposes a verb CLI — the installed `linkedin-cli` console command (or `python -m linkedin_cli.cli`): `session open/close`, `login`, `whoami`, `search`, `profile`, `status`, `connect`, `message`, `thread` — over a **bind+connect** transport — a session owner `browser.bind()`s the browser, clients `chromium.connect()`. **Output contract** (in the `cli.py` docstring so it travels with the package): each verb returns a result dict, rendered as a brief human summary by default or the full dict with `--json` (redirect with `>` to save; no `--out`); errors → stderr + non-zero exit. The daemon owns its browser in-process and consumes the library directly; launch/cookie-persistence glue stays in `openoutreach/linkedin/browser/launch.py`. **Auth is a page-state machine** (`page_state.py`: `classify_page` judges the page by URL *path* only, `@transition(when=,then=)` contracts enforce pre/post state raising `IllegalPageTransition`, `PageFlow` is the generic observe→act engine; `auth.py`: the login flow as declared `@auth_flow.transition` actions + `authenticate()`, shared by the CLI verb and the daemon — no duplicated login path). **Proxy support** (optional): `linkedin_cli/conf.py` exposes `BROWSER_PROXY_SERVER`, `BROWSER_PROXY_USERNAME`, `BROWSER_PROXY_PASSWORD` — set to enable HTTP/SOCKS5 proxying. Default is `None` (direct connection, recommended for self-hosted where users run the daemon on their own IPs). For cloud deployments, mobile proxies ($50-150/month unlimited bandwidth, 1 IP per 2-3 profiles = $25-75/profile) are preferred over residential pay-per-GB proxies. **Never use datacenter/Elastic IPs** — LinkedIn actively blocks cloud provider IP ranges. **Bandwidth optimization** is enabled by default: the browser blocks third-party images/fonts/stylesheets/media while preserving all LinkedIn resources, reducing bandwidth 60-70% with zero functionality loss. See `docs/PROXY_GUIDE.md` for cost comparisons and setup. CRM/campaign/scheduling/ML stay in this project. (Extracted to its own repo + submodule; OpenOutreach consumes it as a dependency.)
- **Entry**: `openoutreach/cli.py` — Click-based CLI. `rundaemon` starts the multi-profile daemon (`openoutreach/core/daemon.py`): scans all active `LinkedInProfile` records with credentials, manages a session pool (one Playwright browser per profile), claims tasks scoped by `linkedin_profile_id`, and round-robins execution across all users. Profiles are re-scanned every 5 minutes so new users start automatically. `runserver` starts FastAPI on port 8001. Docker `start` script handles Xvfb/VNC, starts Next.js, and FastAPI server. **Cookie refresh**: after each successful task completion, the daemon calls `_save_cookies(session)` to persist the current Playwright storage state back to MongoDB.
- **Lead/Deal separation**: `Lead` = a discovered person (created immediately on discovery, visible in campaign leads list). `Deal` = the Lead's relationship to a Campaign (created at discovery time to link leads to campaigns). **ALL discovered leads appear in campaign leads list**, regardless of AI qualification status. The AI qualification is purely advisory — operators can manually qualify/disqualify any lead via UI actions to override AI classification and prevent losing good leads to classification errors. `Deal.state` tracks the lead's journey through the funnel, with a "Qualified" badge shown for AI-approved leads but all leads remaining actionable.
- **State machine**: `openoutreach/crm/models/deal.py:DealState` (OpenOutreach-owned `TextChoices`) — DISCOVERED → QUALIFIED → READY_TO_CONNECT → PENDING → CONNECTED → COMPLETED / FAILED, plus the off-funnel **NO_EMAIL** (enrichment found no address — held out of the connect pool). `Deal.state` is a CharField with `DealState` choices (no Stage model). **DISCOVERED** is the initial state for all newly added leads; AI qualification moves them to QUALIFIED, but operators can manually transition any DISCOVERED lead to QUALIFIED via UI actions. The funnel is **not** in `linkedin_cli`: the library's connect/status verbs only *observe* three of these (QUALIFIED/PENDING/CONNECTED) off the LinkedIn UI and return them as plain strings over the CLI boundary, where the task handlers lift them via `DealState(value)`. The library keeps its own internal `linkedin_cli.enums.ProfileState` (those 3 UI states) — OpenOutreach no longer imports it. `Outcome` (converted/not_interested/wrong_fit/no_budget/has_solution/bad_timing/unresponsive/unknown) on Deal.outcome. `Lead.disqualified=True` = permanent exclusion (never shown in any campaign). LLM rejections = FAILED Deals with wrong_fit outcome (campaign-scoped — same lead can be FAILED in one campaign and QUALIFIED in another). **Contact capture on connection**: when a Deal first enters CONNECTED, `set_profile_state` fires a best-effort `Lead.capture_contact_info(session)` (the moment LinkedIn exposes a 1st-degree connection's email/phone) — failures are logged and never roll back the transition; `AuthenticationError` propagates. Lead email storage is one field per source: `Lead.contact_info` (raw LinkedIn overlay, written here) + `Lead.api_email` (enrichment-API result, writer lands with the finder).
- **Task queue**: `Task` model (persistent) with `linkedin_profile_id` and `user_id` fields for multi-tenant scoping. Three types: `connect`, `check_pending`, `follow_up`. Handlers in `openoutreach/linkedin/tasks/`, signature: `handle_*(task, session, qualifiers)`. Task rows are **lazy**: `payload = {"campaign_id": <id>}` only; the handler resolves the concrete target at execution time via a single eligibility query. `Task.objects.claim_next(linkedin_profile_id=...)` atomically claims the next due task for a specific profile — the daemon calls this per-profile in round-robin. Slot creation is centralized in `openoutreach/core/scheduler.py` — no other module inserts Task rows. The planner exposes one function per type (`plan_connect_window`, `plan_follow_up_window`, `plan_check_pending_window`); each operates in **Smart** or **Manual** mode based on `SiteConfig.enable_smart_rate_limiting` and stamps `linkedin_profile_id` + `user_id` on every created task. **Smart mode** (default OFF): scheduler reads `aggressiveness_preset` from `rate_limit_presets.py`, applies time-of-day weighting, and adjusts for detectability score via `SmartRateLimitContext`. **Manual mode**: scheduler uses fixed `SiteConfig.velocity` (actions/hr). `SiteConfig.load(user_id=...)` loads per-user settings so each user's active hours and rate limits are independent. `reconcile(session)` runs on daemon idle per-profile: recovers stale RUNNING tasks, then iterates campaigns × planners. On 401 (`AuthenticationError`), the daemon marks the task FAILED and pauses the profile; reconcile picks the type up on the next cycle.
- **ML pipeline**: GPR (sklearn) + BALD active learning + LLM qualification. Per-campaign models stored in `Campaign.model_blob` (DB).
- **Config**: `SiteConfig` MongoDB model (LLM_PROVIDER, LLM_API_KEY, AI_MODEL, LLM_API_BASE, FINDER_API_KEY, plus account-level follow-up guardrails `ai_writing_style` / `ai_say_rules` / `ai_avoid_rules`, active hours config `enable_active_hours` / `active_start_hour` / `active_end_hour` / `active_timezone` / `active_days`, smart rate limiting toggle `enable_smart_rate_limiting` + `aggressiveness_preset` [very_slow/slow/average/aggressive/very_aggressive], and manual pacing field `velocity` [actions per hour, only used when smart=OFF] — all editable via FastAPI endpoints and the frontend Settings page; `finder_api_key` is the BetterContact email-finder key, blank disables enrichment (see `emails/finder.py`); `llm_provider` chooses between OpenAI/Anthropic/Google/Groq/Mistral/Cohere/openai_compatible, `llm_api_base` only consulted when provider is `openai_compatible`), `conf.py:CAMPAIGN_CONFIG` (timing/ML defaults), `linkedin_cli/conf.py` browser constants (`BROWSER_*`, `HUMAN_TYPE_*`, `BROWSER_HEADLESS`), `conf.py` onboarding defaults (`DEFAULT_*_LIMIT`), `conf.py:FASTEMBED_CACHE_DIR` (persistent model cache, defaults to `<project>/.cache/fastembed/`), Campaign/LinkedInProfile models (MongoDB). `VOYAGER_REQUEST_TIMEOUT_MS` lives in `linkedin_cli/api/client.py` (constructor default on `PlaywrightLinkedinAPI`). `linkedin_cli/conf.py:DUMP_PAGES` (default `False`) — enable to save page HTML snapshots for fixture collection. **Note**: `conf.py` still has deprecated `ENABLE_ACTIVE_HOURS` / `ACTIVE_START_HOUR` / `ACTIVE_END_HOUR` / `ACTIVE_TIMEZONE` constants for backwards compatibility, but they are no longer read by the daemon or scheduler — both read from `SiteConfig`.
- **Lazy accessors**: `Lead.get_profile(session)` is a live Voyager scrape that also updates `Lead.cached_profile` (JSON) on success; `Lead.get_urn(session)` reads the `urn` column and falls back to a scrape; `Lead.get_embedding(session)` lazily scrapes + embeds on first access, then caches the 384-dim bytes on the row. `Lead.capture_contact_info(session)` scrapes the LinkedIn contact-info overlay (1st-degree only) and persists it raw to `Lead.contact_info` once — idempotent on non-null (even an empty result counts as "tried"). `Lead.resolve_api_email()` resolves a work email via the finder (`emails/finder.py`, URL-only, no session) and persists `Lead.api_email`. Tri-state: returns **True** on a hit (cached, never re-resolved), **False** on a genuine miss (finder ran, found nothing — the qualify hook parks the Deal in the OpenOutreach-owned `DealState.NO_EMAIL` state via `set_profile_state`, holding it out of the connect pool), **None** when the finder couldn't run (no key set, or service unreachable — `FinderUnavailable`, leave QUALIFIED to retry). A miss is free to retry — BetterContact bills only usable hits. Fired at qualification (`pipeline/qualify.py`, right after the QUALIFIED promotion) — enrichment only ever runs on qualified leads. `Lead.embed_from_profile(profile)` reuses an in-hand profile dict to skip the scrape (used by `create_enriched_lead`). `Lead.to_profile_dict()` returns a minimal `{lead_id, public_identifier, url, meta}` dict (no `profile` key). `AccountSession.campaigns` (cached_property, list). `AccountSession.self_profile` (cached_property, re-discovers via Voyager on first access per session — no DB cache).
- **Deal summaries**: `Deal.profile_summary` and `Deal.chat_summary` are lazy, mem0-style JSON fact lists built on demand and updated incrementally. `openoutreach/core/db/summaries.py` is the single boundary — `materialize_profile_summary_if_missing(deal, session)` fires on the first follow-up touch (one Voyager re-scrape per `(lead, campaign)` lifetime), `update_chat_summary(deal, new_messages, *, seller_name)` folds newly-synced ChatMessages into the summary via `reconcile_facts`, which routes new facts through mem0's UPDATE prompt to apply ADD/UPDATE/DELETE/NONE events (no naive append-and-dedup). **Only incoming (lead) messages reach fact extraction** — outgoing seller messages are filtered at the boundary so `chat_summary` stores facts about the lead, never the seller's pitch. A one-sided burst of outgoing messages short-circuits the LLM call entirely. **Identity binding (required):** `extract_facts`, `update_chat_summary`, and `reconcile_facts` all require a `seller_name` kwarg, sourced via `seller_name_from(session)` (first_name from `session.self_profile`, username fallback) and injected into the system prompt so the LLM stops inferring `the lead's name is Diego` from a lead reply like `"Hola Diego, gracias..."`. The mem0 reconcile prompt also receives the binding and is instructed to DELETE stored facts that describe the seller as if they were the lead — so previously-contaminated rows *should* be cleaned up on the next sync that produces a conflicting fact, though this is best-effort (mem0's vendored prompt is example-heavy and the cleanup hint is one prepended sentence). Dormant deals with no new messages stay contaminated until eager cleanup. The follow-up agent consumes `profile_summary + chat_summary + last 6 ChatMessage rows` instead of flat profile fields; its prompt (`follow_up_agent.j2`) carries the same `Me`→`self_name` binding under the verbatim-messages header and now appends account-level `SiteConfig` guardrails (`ai_writing_style`, `ai_say_rules`, `ai_avoid_rules`) so operators can steer tone, phrases to emphasize, and phrases/promises to avoid from Settings without editing the template. The fact-extraction prompt is vendored at `openoutreach/core/db/summaries.py:_FACT_EXTRACTION_PROMPT`; mem0's `DEFAULT_UPDATE_MEMORY_PROMPT` and `get_update_memory_messages` are vendored under `openoutreach/core/vendor/mem0/configs/prompts.py` (mirroring upstream paths so future syncs are a clean diff). No `mem0ai` runtime dependency — avoids qdrant/grpcio/sqlalchemy transitive bloat.
- **Desktop daemon** (Phases 3-8 complete): Remote daemon that runs on user's desktop using their residential IP and real browser. Three components: `core/remote_client.py` (async HTTP client for daemon-backend communication, handles task claiming, result reporting, cookie sync, session state), `core/browser_detect.py` (automatic detection of Chrome/Edge/Safari on Windows/macOS), `core/daemon_remote.py` (desktop daemon that executes tasks locally while coordinating with centralized backend — supports all task types, active hours, config refresh, graceful error handling). **Desktop app** (Phase 4-8): System tray application with `desktop/app.py` (main tray UI with start/stop, status, menu, auto-update checker), `desktop/auth.py` (system keychain integration via keyring for secure credential storage), `desktop/config.py` (persistent app configuration), `desktop/protocol_handler.py` (openoutreach:// URL callback handler for web login flow), `desktop/updater.py` (GitHub releases update checker — checks every 6 hours, platform-specific downloads, non-intrusive notifications). Run with `openoutreach desktop` command. The remote daemon is an alternative to the cloud daemon for users who want to avoid proxy costs ($25-75/profile/month) by running automation on their own machine. See `docs/DESKTOP_APP.md` for full implementation plan (Phases 1-8 complete, Phase 9 testing pending). Desktop dependencies in `desktop/requirements.txt` (pystray, keyring, pyinstaller, packaging). Build with `desktop/build.py`. Distribution via GitHub releases (`.github/workflows/desktop-build.yml`) creates DMG (macOS), NSIS installer + standalone exe + MSIX (Windows) on `desktop-v*` tags.
- **App structure**: all modules nested in the single `openoutreach/` package: `core` (engine — daemon, remote daemon, Task queue + scheduler, Campaign/SiteConfig/Task, llm.py, onboarding, follow-up agent), `linkedin` (channel — browser, discovery pipeline, ML, LinkedInProfile/SearchKeyword/ActionLog, task handlers), `emails` (channel — email outreach, Layer 1 WIP), `crm` (Lead with embedding/Deal), `chat` (ChatMessage), `api_v2` (FastAPI routers, dependencies, schemas), `mongodb` (models, connection, DAL). One engine, N channels; `core` imports channel code only at wiring points. LinkedIn settings API endpoints query `LinkedInProfile` through minimal field projections and return structured JSON responses. The frontend Settings page is now a tabbed workspace with `LinkedIn Connection`, `Profile`, `Rate Limits`, and `LLM / AI Settings` tabs; the last two surface all persisted `SiteConfig` pacing fields (`daily_*`, `velocity`, `cooldown_minutes`) plus account-level follow-up guardrails (`writing_style`, `say_rules`, `avoid_rules`) instead of leaving those pages disconnected from `/settings`. The frontend credential modal now asks only for LinkedIn email and password, with the optional session cookie tucked into a collapsed dropdown section that explains step-by-step DevTools extraction, notes that `li_at` is not available from the browser console because it is `HttpOnly`, and warns that extensions are optional and higher trust. Credential create/update/verify auto-attach (or create) the user's `LinkedInProfile`, sync its daemon login fields from the stored credential, and the browser/session code persists cookies via `cookie_data_encrypted` only, so profile selection/display username are discovered after login instead of entered manually. Deleting a credential is now a true delete: it removes the credential row and clears the linked profile's synced login fields/cookies so failed test saves do not linger as undeletable invalid entries. The credential cards consume the frontend's camel-cased API payloads, show `Profile not available` when LinkedIn has not exposed a username yet, safely render missing timestamps, allow health details to toggle open/closed, and render audit logs on zinc panels with readable light text. The LinkedIn Connection tab now refreshes setup guide/status/instructions/credentials together, shows a visible refresh spinner, and reads setup-status fields from the camel-cased API shape (`linkedinProfile`, `linkedinCredentials`, `setupComplete`, `setupProgress`), so the Setup Status counts and progress stay in sync with the stored credentials list.
- **Analytics contract**: campaign list stats (`openoutreach/api/serializers/campaigns.py`) expose live `connectionsSent`, `connectionsAccepted`, `messagesSent`, `messagesReplied`, and zero-safe rates derived from `ActionLog`, `ChatMessage`, and current `DealState` counts — no hard-coded fallback percentages. The overview page (`frontend/src/app/(dashboard)/analytics/page.tsx`) now reads from `openoutreach/api/views/campaigns.py:AnalyticsOverviewView`, which supports real `campaign_id` + `period` filtering and returns live overview totals plus per-campaign metrics for the selected window. The per-campaign analytics API (`openoutreach/api/views/campaigns.py:CampaignAnalyticsView`) also uses zero-safe percentage math, actual `DealState` enum values, real 7/30-day aggregates, and reply timestamps from `ChatMessage.creation_date` instead of `Deal.creation_date`.
- **Data dir**: `data/` holds persistent state (MongoDB connection via Atlas or local). Docker users mount volumes at `/app/data` for local file storage.
- **Docker**: Playwright base image. When `ENABLE_VNC=true`, starts x11vnc on port 5900 and noVNC websockify web viewer on port 6080. The frontend Settings → LinkedIn Connection tab embeds a live noVNC iframe viewer (`/components/settings/vnc-viewer.tsx`) so operators can interact with LinkedIn challenges, CAPTCHAs, or security verifications directly from the platform without needing an external VNC client or SSH tunnel. `BUILD_ENV` arg selects requirements.
